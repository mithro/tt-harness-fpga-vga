# Hardware validation: design

Date: 2026-11-23. Status: draft for the owner's approval.

This replaces the "Validate" and "Sharing the boards" sections of
`2026-11-23-tt-harness-fpga-vga-design.md`. Those were written before anyone had read
the board firmware, the capture tooling and the Raspberry Pi daemon closely. An
independent review did that reading and found that the earlier design could not work
as written. This document is built on what that review verified in the code.

Lines marked **(owner)** record something the owner said. **(call)** marks the
author's decisions. **(verified)** means read in the named source; **(inferred)**
means reasoned, not yet seen; **(unknown)** needs an experiment on a board.

## What has to be true for a result to mean anything

The simulated reference (`reference.json` and its raw dump) describes a design that:

1. is configured into the FPGA with every flip-flop and RAM at zero;
2. sees no clock edge at all until clock 0;
3. sees `rst_n` low for the rising edges of clocks 0 to 9, high from clock 10;
4. sees fixed `ui_in` and `uio_in` values for the whole run;
5. has `uo_out` sampled after each rising edge, while the clock is high.

A board comparison is only valid if the board reproduces all five. The earlier design
reproduced none of 2, 4 and 5 reliably. The rest of this document is how to get them.

## What the earlier design got wrong

- **Loading through the daemon runs the design before the harness has control.** The
  daemon's `POST /designs/<name>/enable` loads the FPGA and then runs the SDK's
  project-enable path, which pulses reset once and starts a 100 Hz PWM clock with
  `rst_n` released. During the load itself the previous design's clock keeps
  running. So the design receives an unknown number of clocks out of reset before any
  harness command can arrive **(verified:** fpgas.online-tt `designs.py`, SDK
  `fpga_mux.py`, `demoboard.py`**)**.
- **`POST /bitstream` is not a loader and is not polite.** It only stores a file on
  the Pi, keeps 16, and evicts the oldest, including visitors' uploads
  **(verified)**.
- **"Start the clock and the capture together" is two MicroPython statements.** At
  500 kHz that is an unknown offset of many clocks, not zero **(verified by
  arithmetic; statement latency is tens of microseconds)**.
- **The existing capture tool samples after the falling edge.** The reference records
  after the rising edge. They agree only for designs with no negative-edge state and
  no combinational path from the clock to an output **(verified:** `ttcap`
  default `edge="falling"`**)**.
- **The inputs are not what the reference assumes on the Welland boards.** The Pi's
  Pmod HAT wires `ui_in[1:3]` and `uio[1:3]` to the same three Pi GPIOs, so each pair
  is one electrical net **(verified:** tt-fpga pin mapping document**)**. `ui_in[0]`
  has been seen reading 1. Undriven `uio` pins sit wherever the Pi's pull resistors
  put them **(inferred)**.
- **Driving inputs from the MCU can create contention.** The MCU driving `ui_in[k]`
  fights a design that drives `uio[k]` for k = 1 to 3, and fights any Pi GPIO that is
  an output. Loading a design that drives `uio` can itself fight a Pi output.
- **Sync periods prove nothing at full speed.** With the clock generated by the MCU,
  hsync and vsync periods are 800 and 420,000 clocks by construction; they exercise
  only the counters, not the pixel logic where the slow paths are.
- **The boards have no locking.** A visitor who merely opens a board's page connects
  a serial client, and that client soft-resets the board if the REPL is silent for
  100 ms. A harness capture would be killed; a visitor's terminal would be flooded
  by the harness's stream **(verified:** daemon bridge and commander app**)**.
- **The idle display cannot be reloaded through the API.** Its name is reserved. The
  daemon restores it by itself once the board is back in the SDK's start state and
  quiet for about 60 s **(verified)**.

## Design

### Loading: the harness loads the FPGA itself, with the clock held low

In one REPL session on the board **(call)**:

1. Stop the SDK's PWM clock with the SDK's own call, then drive the clock pin low,
   push-pull, and keep it driven for the whole session. Never reconfigure the clock
   pad while PWM is running: that takes the pad away from PWM until a hard reset
   **(verified in the capture project's findings)**.
2. Drive `rst_n` low.
3. Stream the bitstream into a RAM buffer over the REPL and call the SDK's SPI loader
   function directly (as the daemon does internally), not the project-enable call.
   This configures the FPGA without running the enable path.
4. The design now sits configured, all-zero, clock low, reset asserted. No clock has
   reached it.

Nothing is written to the board's filesystem or to the Pi.

### Clocking and capture: one PIO program owns the clock

A single PIO state machine generates the project clock with side-set and samples
`uo_out` (eight contiguous GPIOs) during the high phase of each clock **(call)**. Then:

- one sample is exactly one clock, by construction;
- clock 0 is the first edge the program ever emits, so there is no offset to search;
- the sample point matches the reference's;
- with blocking pushes and the DMA buffer re-armed only when the host has taken the
  previous one, a slow link stalls the clock instead of dropping samples. The capture
  is lossless at whatever rate the link gives, with no overrun case to handle.

`rst_n` is outside the PIO's pin window on this board, so the CPU releases it while
the PIO holds the clock low between edge 9 and edge 10. The program runs N clocks for
edges 0 to 9, pauses, and continues.

Constraints from the earlier capture work **(verified)**: use PIO block 1, since
block 0 holds the FPGA loader; set the GPIO base to 16 after removing any program;
pin numbers in `wait` and `in_base` are absolute; remove the program on teardown, or
the 32 instruction slots fill after about ten runs; hard interrupt handlers must be
module-level functions.

### Inputs: measure first, drive little

Before any design is loaded on a board, a **pin census** of that board **(call)**:

- on the Pi, read-only, the mode and pull of every GPIO wired to the Pmod HAT, and
  whether the SPI kernel modules are loaded;
- on the board's MCU, read every Tiny Tapeout pin as an input under pull-up and then
  under pull-down. A pin that follows the pull has nothing driving it. A pin that
  ignores both is driven; a pin that follows only one is being pulled the other way.

The census decides, per board, which `ui_in` bits the MCU may drive and what value
every undriven net sits at. Rules:

- The MCU never drives `uio`.
- The MCU drives a `ui_in` bit only if the census shows nothing but pulls on it.
- The MCU never drives `ui_in[1:3]` for a design whose reference shows it ever
  enabling `uio[1:3]` as outputs.
- A design that enables any `uio` output is not loaded on a board where the census
  shows a Pi GPIO driving that net.
- Do not switch the SDK into its "MCU controls inputs" mode. It re-creates every pin
  and arms a manual-clock monitor that can stop the clock **(verified)**. Drive pins
  directly.

The reference must describe what the board actually presents. So the reference stage
gains a **board stimulus profile**: the `ui_in` value the board can set, the level of
each `uio` net, and the `ui_in[1:3]`-to-`uio[1:3]` ties. A reference is generated per
profile, and its key includes the profile. Two profiles exist to start with: `ideal`
(what plan 1 produced; a board at home with nothing attached) and one per Welland
board from its census.

### Does the design care about anything the board cannot reproduce?

Computed per design in simulation, before any board time is spent **(call)**:

- **Pre-reset sensitivity.** Simulate again with random initial register state
  (two seeds). If the output from clock 10 onward is identical, the design's picture
  is determined by reset alone. If not, it relies on power-up state, and only the
  zero-state load above can match it; record the fact.
- **Phase sensitivity.** Record `uo_out` in the low phase too. A design whose
  low-phase and high-phase values differ has negative-edge or clock-to-output
  combinational behaviour; record it.
- From the tool logs: latches inferred, combinational loops, more than one clock,
  SPRAM use.

These flags do not exclude a design. They explain a mismatch when one happens, and
they pick the easy designs for the first runs.

### Comparison

The board's samples and the reference dump are both one byte per clock from clock 0.
Compare them directly:

- `exact`: every byte equal over the compared length;
- `mismatch`: report the first differing clock, the differing bits, and the fraction
  of clocks that differ, then cut frames from both and write a difference image.

A mismatch in every clock, or by a constant offset, points at the harness. A mismatch
in particular bits from a particular clock points at the design or the build. Every
burst of work on a board is bracketed by a calibration design; if the calibration
design does not come out `exact`, nothing in that burst counts.

### Full speed: exact pixel windows, and a margin

Replace the sync-period check **(call)**. The same PIO program runs the clock at a
divisor of the system clock (150 MHz / 6 = 25.0 MHz) with no flow control, counts N
clocks from reset, then captures a window of up to about 350,000 samples into RAM
(the free heap measured on these boards is about 426 KB). The window is compared
clock-exact with the same clocks of the reference, allowing a constant output latency
of zero to two clocks that must be stable (the pad delay reported by nextpnr is longer
than one 25 MHz period). Moving the window across runs covers whole frames.

Running the same check at higher divisors' rates (27.3, 30, 33.3 MHz) measures each
design's real margin on that board. This is the evidence the "missed timing on paper"
question needs: not whether the syncs look right, but at what frequency the pixels
stop being exact.

Whether nextpnr's iCE40 timing figures are a slow-corner estimate, and so pessimistic
at room temperature, could not be established from local sources **(unknown)**. The
sweep answers it empirically.

### Sharing the boards

There is no lock, so the protocol is to stay out of the way and leave quickly:

1. Use a board only when its status shows `clients` 0 and the idle display `loaded`.
   `waiting`, `in use` or `left: <a design>` mean someone was or is there: skip it.
2. Take the claim file (between Claude sessions).
3. Open one serial connection and check that `clients` is now exactly 1.
4. Work in a burst of a few minutes. Re-read the status between designs. If
   `clients` exceeds 1, stop at once, record `capture-error: board taken`, clean up
   and leave.
5. Clean up: remove PIO programs, release every pin, soft-reset the board into the
   SDK's start state, disconnect.
6. About 70 s later, confirm the status is back to `loaded`.

Never use `POST /bitstream` or `POST /designs/.../enable`.

How to do step 5, as observed on fpga-4 on 2026-11-23 by the capture project's
session (the first of these facts from a real board, not from reading code): a
`machine.soft_reset()` sent from the raw REPL leaves the board in the raw REPL without
running `main.py`, and the daemon then reports `left: the SDK is not running`. The
sequence that works is to leave the raw REPL (Ctrl-B) and then send Ctrl-D from the
friendly REPL. The SDK restarts into its factory-test design and the status returned
to `loaded` about 75 s later.

The harness's sample stream is binary and fast; any other client on the serial bridge
would see it. That is another reason to work only when `clients` is 0.

Board identity is the USB serial number, never a switch port: the port tables in
different documents disagree.

### Transport

The owner's earlier rule for the capture project was that the daemon's serial bridge
is for debugging and real captures should own the serial device on the Pi. This
design uses the bridge anyway **(call, needs the owner's agreement)**, for one
reason: the bridge is the only path on which a member of the public using the board
is visible to the harness and the harness to them. Taking the device on the Pi would
hide both. The bridge drops a client that falls 256 KB behind; with flow control at
the PIO that cannot lose data, only slow the clock.

## Order of work

1. **Pin census on fpga-4.** Read-only on the Pi; pull-up and pull-down reads on the
   board. Also record the RP2350 stepping and the board revision. Result: the first
   board stimulus profile, and the answer to whether inputs can be set at all.
2. **Recoverability.** Show that after the harness's own load and a PIO-owned clock
   pin, a soft reset returns the board to stock behaviour and the daemon restores the
   idle display. If it does not, stop and rethink before touching another board.
3. **Clock-exact capture from clock 0** of `calibration/tt_um_vgacal_counter` and
   `tt_um_vgacal_prbs` (animated, so alignment errors show), compared byte for byte
   with their references.
4. The other three calibration designs, then the three shared designs that meet
   timing.
5. **Full-speed windows** on the calibration designs, then the frequency sweep on the
   five designs that miss timing on paper.
6. A second board, to see board-to-board variation.

Steps 1 to 3 are experiments whose results may change the rest. The implementation
plan covers 1 to 3 in detail and treats 4 to 6 as an outline to be confirmed after.

## What this changes elsewhere

- The reference stage gains board stimulus profiles, the low-phase dump and the
  sensitivity flags.
- The frame hasher must handle a capture of millions of samples without holding every
  frame in memory.
- The published bitstream is the validated bitstream: nothing is added to the FPGA
  wrapper. A signature register inside the wrapper was considered and rejected for a
  first pass, because it would make the validated and published bitstreams differ.
- The QSPI Pmod emulation needs rethinking: the MCU cannot drive `uio` on a board
  whose HAT ties `uio[1:3]` to `ui_in[1:3]`, and the FPGA's SPRAM is not cleared by
  reconfiguration **(inferred)**, so "all-zero memory" would not hold. Left for the
  plan that covers those 35 designs.
- The library entry rule becomes: `exact` in the slow capture, and `exact` in
  full-speed windows at the design's clock with a margin. The size of the margin, and
  whether a design may enter despite missing timing on paper, is the owner's
  `verdict_passes()`.
